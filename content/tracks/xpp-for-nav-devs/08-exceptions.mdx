## throw error(...) is two things on one line

You have seen `error()` since lesson 1. It writes a red line and returns — it does not stop
anything. What stops things is `throw`:

<Snippet lang="xpp">{`throw error("Cannot post an empty journal.");`}</Snippet>

Read that right to left. `error(...)` writes the message to the Infolog and hands back an
`Exception::Error` value. `throw` then raises that value. Two operations, one line, and the
reason the idiom looks strange until you know it.

The corollary is worth stating plainly:

<Snippet lang="xpp">{`throw Exception::Error;   // raises, but writes NOTHING to the Infolog
throw error("why");       // writes "why", then raises`}</Snippet>

A bare `throw Exception::Error` is technically valid and almost always wrong. The user gets
a failure with no explanation, which is how you end up with support tickets that say only
"it didn't work".

<Compare
  cal={`ERROR('Cannot post an empty journal.');
// Logs, raises and rolls back,
// all in one statement.`}
  xpp={`throw error('Cannot post an empty journal.');
// error() logs and returns a value.
// throw raises it.`}
/>

## try, catch, and the rule that catches everyone

<Snippet lang="xpp">{`try
{
    throw error("something went wrong");
}
catch (Exception::Error)
{
    info("caught it");
}`}</Snippet>

Straightforward. Now the rule that is invisible until it bites:

> An exception thrown inside a transaction **cannot be caught by a `catch` that is also
> inside that transaction.**

The transaction aborts, and the exception goes looking for the innermost `catch` that sits
*outside* the transaction block. Here is Microsoft's own worked example:

<Snippet lang="xpp">{`try
{
    try
    {
        ttsbegin;
        try
        {
            throw error("Throwing exception inside transaction.");
        }
        catch (Exception::Error)
        {
            info("Catch_1: never runs");
        }
        ttscommit;
    }
    catch (Exception::Error)
    {
        info("Catch_2: this is the one");
    }
}
catch (Exception::Error)
{
    info("Catch_3: never runs either");
}`}</Snippet>

Only `Catch_2` runs. `Catch_1` is inside the transaction, so it is skipped entirely;
`Catch_3` is outside but not innermost. Paste that into the sandbox and watch.

Two exceptions to the rule, both to do with concurrency: `Exception::UpdateConflict` and
`Exception::DuplicateKeyException` **can** be caught inside their own transaction — but only
if you name them explicitly. A bare `catch` still will not see them.

<NavCallout>
  **This is the rule that makes C/AL developers distrust X++ error handling.** You wrap a
  posting routine in `try`/`catch`, test it, and the catch never fires — so you conclude
  exception handling is broken and go back to checking return values. It is not broken: the
  catch is in the wrong place. Move it outside the `ttsbegin`/`ttscommit` and it works
  exactly as you expected. The rule exists because a half-rolled-back transaction is not a
  state anything can sensibly recover from, so the platform refuses to hand you control
  while you are still inside one.
</NavCallout>

## retry, and the thing it erases

`retry` is only valid inside a `catch`, and it jumps back to the first line of the
associated `try`. It exists for optimistic-concurrency failures: catch the conflict, wait,
try again.

It has one behaviour nobody expects. **`retry` erases every Infolog message written since
control entered the `try` block.** That is deliberate — a retried operation should not leave
the user reading the failed attempt's output — but the first time you see three log lines
vanish it is unsettling.

<Snippet lang="xpp">{`int attempts;

try
{
    info(strFmt("attempt %1", attempts));
    attempts++;

    if (attempts < 3)
    {
        throw error("not yet");
    }

    info("succeeded");
}
catch (Exception::Error)
{
    retry;
}`}</Snippet>

That logs `attempt 2` and `succeeded`, and nothing else. The first two attempts' messages
were written and then erased.

Guard your `retry` with a counter, always. Nothing else stops it looping forever.
