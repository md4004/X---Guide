## You have to ask for one

In C/AL you never write `BEGIN TRANSACTION`. Every codeunit runs inside a transaction the
platform opened for you, and it commits when the call returns. You only think about it
when you deliberately break it with `COMMIT`.

X++ is the other way round. Nothing is implicit:

<Snippet lang="xpp">{`ttsbegin;
custTable.CreditMax = 50000;
custTable.update();
ttscommit;`}</Snippet>

Leave the pair off and the write fails outright, with an error saying so. That is not the
compiler being strict — it is the same check a real AOS makes, and it exists because a
write outside a transaction has no defined rollback point.

<Compare
  cal={`// Implicit. The platform opened it.
Cust."Credit Limit" := 50000;
Cust.MODIFY;
// Commits when the codeunit returns.`}
  xpp={`ttsbegin;
custTable.CreditMax = 50000;
custTable.update();
ttscommit;`}
/>

## Nesting counts, but only the outside matters

`ttsbegin` can nest. Each one raises a level counter — `ttsLevel` — and each `ttscommit`
lowers it. **Nothing reaches the database until the level returns to zero:**

<Snippet lang="xpp">{`ttsbegin;          // ttsLevel 1
    // work
    ttsbegin;      // ttsLevel 2
        // more work
    ttscommit;     // ttsLevel 1 — nothing committed yet
ttscommit;         // ttsLevel 0 — now it is durable`}</Snippet>

That inner `ttscommit` looks like it commits. It does not. It only decrements. This is what
lets you call a method that manages its own transaction from inside your own transaction
without either of you having to know about the other — the whole thing still lands or fails
as one unit.

## ttsabort throws it all away

Here is the part that catches everyone, and the reason this lesson exists.

<Snippet lang="xpp">{`ttsbegin;
    custTable.AccountNum = "C-OUTER";
    custTable.insert();

    ttsbegin;
        custTable.clear();
        custTable.AccountNum = "C-INNER";
        custTable.insert();
    ttsabort;      // <-- both inserts are gone`}</Snippet>

`ttsabort` does not undo one level. It discards **the entire transaction**, from whatever
depth you call it at, and sets `ttsLevel` straight back to 0. Microsoft's own reference
puts it plainly: it "discards all changes in the current transaction… the database is
rolled back to the original state, where nothing is changed."

If you have a mental model of nested transactions as a stack of savepoints where you can
pop one off — that model is right for SQL Server and wrong for X++.

<NavCallout>
  **There is no `COMMIT` you can sprinkle mid-method.** In C/AL, `COMMIT` ends the current
  transaction and opens a new one, which is how people get long-running jobs to release
  locks — and how they end up with half-posted documents when something fails afterwards.
  X++ has no equivalent, on purpose. A transaction ends where it began, at ttsLevel 0, and
  the only way out early is to abort the whole thing. If you catch yourself wanting a
  mid-method commit, what you actually want is a smaller unit of work.
</NavCallout>

## And if you just forget?

A run that ends with `ttsLevel` still above zero is a defect. This simulator reports it and
rolls the work back, which is the safest reading of an ambiguous situation — you will see
the error in the Errors panel and the data unchanged.
