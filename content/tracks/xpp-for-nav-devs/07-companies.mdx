## One table, not N

This is the biggest structural difference between the two platforms, and it is invisible
until it bites.

In NAV and Business Central, each company gets its own physical tables. `CRONUS$Item` and
`CRONUS Subsidiary$Item` are two separate tables with the same shape. The company you are
in is a property of your session, and the platform picks the table for you.

F&O has **one** `InventTable`. Every row carries a `DataAreaId` — a four-character legal
entity code — and every query you write is silently filtered by it:

<Snippet lang="xpp">{`InventTable inventTable;

while select inventTable
{
    info(inventTable.ItemId);
}`}</Snippet>

That looks unfiltered. It is not. The generated SQL has a `WHERE DATAAREAID = ?` in it that
you never typed. Run it and check the trace — the predicate is right there.

The practical consequence: the same `ItemId` can exist in several companies as several
different rows, with different names, different costs, different everything. `C-1000` in
one entity has nothing to do with `C-1000` in another beyond the coincidence of the key.

  cal={`// Different physical tables.
// Company chosen by the session.
Item.FINDSET;`}
  xpp={`// One table, filtered by DataAreaId.
// The filter is added for you.
while select inventTable
{
}`}
/>

## changecompany: borrow another company for a moment

<Snippet lang="xpp">{`CustTable custTable;

changecompany ("KELT")
{
    select firstonly custTable
        where custTable.AccountNum == "C-1000";

    info(custTable.CurrencyCode);   // KELT's C-1000, not ours
}`}</Snippet>

Inside the block, every buffer reads and writes as though you were signed in to that
company. Outside it, everything is back to normal — including if the block exits through an
error.

The catch, and it is a sharp one: **the buffer has to be declared before the block and
re-selected inside it.** A buffer that already holds a row keeps that row; `changecompany`
changes where the *next* query looks, not what you are already holding.

## crosscompany: all of them at once

<Snippet lang="xpp">{`CustTable custTable;

while select crosscompany custTable
{
    info(strFmt("%1 in %2", custTable.AccountNum, custTable.DataAreaId));
}`}</Snippet>

`crosscompany` removes the filter entirely. You get every row from every legal entity, and
`DataAreaId` becomes a field worth reading, because it is now the only way to tell two
otherwise-identical rows apart.

Use it for reporting and for genuinely cross-entity logic. Do not use it by reflex: a
`crosscompany` query on a large table scans data that the company filter would normally
have excluded, and there is no index that will save you.

<NavCallout>
  **There is no company switch to forget.** In NAV, running the wrong routine while pointed
  at the wrong company writes to the wrong physical table and there is nothing in the code
  to review afterwards — the mistake lives in the session, not the source. In F&O the scope
  is in the statement: `changecompany` is a block you can see, and `crosscompany` is a
  keyword in the query. That makes it auditable, and it makes the failure mode different.
  You will not write to the wrong company by accident; you will write a query that quietly
  returns nothing because you were in the wrong one, and wonder why the table looks empty.
</NavCallout>

## Shared tables exist too

Not every table is company-scoped. `DirPartyTable` — the global registry of people and
organisations — is shared: one row is visible from every company, and it has no
`DataAreaId` filter applied at all. That is how one legal person can be a customer in three
entities without being stored three times.
