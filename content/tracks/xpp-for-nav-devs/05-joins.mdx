## Two buffers, one statement

C/AL has no join. You loop the header table and, inside the loop, filter and read the lines
— which is one query per header, and the reason so many NAV reports get slow at exactly the
moment the data gets interesting.

X++ joins in the `select` itself:

<Snippet lang="xpp">{`SalesTable salesTable;
SalesLine salesLine;

while select salesTable
    join salesLine
    where salesLine.SalesId == salesTable.SalesId
{
    info(strFmt("%1 / %2", salesTable.SalesId, salesLine.ItemId));
}`}</Snippet>

Both buffers are populated on every pass. The `where` after the joined table is the join
condition — X++ does not have a separate `on` keyword, which reads oddly at first and then
stops mattering.

One statement, one round trip. Check the SQL trace after running it and you will see a
single `SELECT` with an `INNER JOIN`, whatever the row count.

<Compare
  cal={`SalesHeader.FINDSET;
REPEAT
  SalesLine.SETRANGE("Document No.", SalesHeader."No.");
  IF SalesLine.FINDSET THEN
    REPEAT
      MESSAGE(SalesLine."No.");
    UNTIL SalesLine.NEXT = 0;
UNTIL SalesHeader.NEXT = 0;`}
  xpp={`while select salesTable
    join salesLine
    where salesLine.SalesId == salesTable.SalesId
{
    info(salesLine.ItemId);
}`}
/>

## The four kinds

| Written              | Means                                                       |
| -------------------- | ----------------------------------------------------------- |
| `join`               | Inner join. Only rows that match on both sides.             |
| `outer join`         | Left outer. Every outer row, with the joined buffer empty when there is no match. |
| `exists join`        | Keep the outer row **if** a match exists. No fields fetched. |
| `notexists join`     | Keep the outer row **if no** match exists. No fields fetched. |

`exists join` and `notexists join` are the two most useful and the two most often missed.
They answer "which customers have ordered?" and "which customers never have?" without
fetching a single sales-order field, and — crucially — without duplicating the outer row
once per match:

<Snippet lang="xpp">{`CustTable custTable;
SalesTable salesTable;

while select custTable
    exists join salesTable
    where salesTable.CustAccount == custTable.AccountNum
{
    info(custTable.AccountNum);
}`}</Snippet>

A customer with six orders appears once. Write that as a plain `join` and they appear six
times, which is a bug you will not notice until someone sums a column.

<NavCallout>
  **The join condition lives in a `where`, not an `on`.** Every join in X++ is written
  `join otherTable where otherTable.Key == thisTable.Key`, and if you omit the `where` you
  get a cross join — every row against every row — with no warning. SQL would at least look
  odd; X++ looks almost right. When a joined query returns a suspiciously round and
  suspiciously large number of rows, a missing join condition is the first thing to check.
</NavCallout>

Run each of the tasks below and open the SQL trace. You will see `exists join` compile to
an `EXISTS (SELECT 1 ...)` subquery rather than a join — that is exactly how F&O compiles
it, and it is why it cannot duplicate outer rows.
