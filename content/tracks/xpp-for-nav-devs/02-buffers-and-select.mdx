## A buffer is just a variable

In C/AL you write `Item.GET('1000')` and the `Item` variable holds a record. X++ works
the same way, and the declaration looks like any other variable — type first, then name:

<Snippet lang="xpp">{`InventTable inventTable;`}</Snippet>

That is a **table buffer**. It holds at most one record at a time, it starts empty, and
you fill it with a `select`. By convention the variable is the table name with a lowercase
first letter, which is why so much X++ reads like doubled-up names.

To read one record, ask for one:

<Snippet lang="xpp">{`select firstonly inventTable
    where inventTable.ItemId == "F-100";`}</Snippet>

`firstonly` matters. Without it the database still fetches a whole result set, and you
have paid to read everything in order to look at one row. With it, the generated SQL gets
a `LIMIT` — you can see that for yourself in the SQL trace after any run.

## When the select finds nothing

There is no `IF Item.GET(...) THEN`. A `select` that matches nothing leaves the buffer
empty rather than raising anything, and you test it by reading a field:

<Snippet lang="xpp">{`select firstonly custTable
    where custTable.AccountNum == "NOPE";

if (!custTable.AccountNum)
{
    info("No such customer");
}`}</Snippet>

An empty buffer returns the type's default for every field — `""` for a `str`, `0` for an
`int`, and a `RecId` of `0`. That last one is the idiomatic test in real code:
`if (custTable.RecId)`.

## Looping with while select

This is where the two languages part company. C/AL makes you drive the cursor yourself:

<Compare
  cal={`Item.SETRANGE("Item Category Code", 'FURNITURE');
IF Item.FINDSET THEN
  REPEAT
    MESSAGE(Item.Description);
  UNTIL Item.NEXT = 0;`}
  xpp={`while select inventTable
    where inventTable.ItemGroupId == "FURNITURE"
{
    info(inventTable.ItemName);
}`}
/>

`while select` is a single statement that declares the filter and the loop together. There
is no `FINDSET`, no `NEXT`, and no `SETRANGE` — the `where` clause _is_ the filter, and it
belongs to the same statement that opens the cursor.

<NavCallout>
  **There is no `FINDSET`, and that is not an omission.** In C/AL, `SETRANGE` and `FINDSET`
  are separate steps because the filter lives on the record variable and survives between
  calls. In X++ the filter belongs to the `select` statement, so it cannot leak into the
  next query by accident — a whole class of C/AL bug, where a stale `SETRANGE` silently
  narrows a later `FINDSET`, simply cannot happen. The cost is that you cannot build a
  filter up conditionally across several lines. When you genuinely need that, the answer is
  the `Query` object model, which is out of scope here.
</NavCallout>

## Reading is not writing

One more thing before the tasks. A buffer filled by a plain `select` is **read-only**. If
you intend to change what you read, say so up front with `forupdate`:

<Snippet lang="xpp">{`ttsbegin;
while select forupdate inventTable
    where inventTable.ItemGroupId == "FURNITURE"
{
    inventTable.Blocked = NoYes::Yes;
    inventTable.update();
}
ttscommit;`}</Snippet>

Leave out `forupdate` and the update fails, because the record was not selected for update.
That is the database protecting you from a lost update, not the compiler being fussy.
Transactions are the next lesson; for now, copy the `ttsbegin`/`ttscommit` pair when you
write.
