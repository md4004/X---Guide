## The same result, a hundred times the cost

Here are two pieces of code. They leave the database in exactly the same state.

<Snippet lang="xpp">{`// One statement per row.
ttsbegin;
while select forupdate inventTable
    where inventTable.ItemGroupId == "FURNITURE"
{
    inventTable.Blocked = NoYes::Yes;
    inventTable.update();
}
ttscommit;`}</Snippet>

<Snippet lang="xpp">{`// One statement, full stop.
ttsbegin;
update_recordset inventTable
    setting Blocked = NoYes::Yes
    where inventTable.ItemGroupId == "FURNITURE";
ttscommit;`}</Snippet>

Run both and look at the SQL trace. The loop issues a `SELECT` and then one `UPDATE` per
row. The `update_recordset` issues a single `UPDATE` that the database applies to the whole
set. Over four seeded items the difference is invisible. Over forty thousand it is the
difference between a job that finishes and a job somebody kills.

This is why the SQL trace is a panel and not a debug flag. It is the only place the cost of
your code is visible before production shows you.

## The three statements

<Snippet lang="xpp">{`update_recordset inventTable
    setting Blocked = NoYes::Yes, ItemGroupId = "STOPPED"
    where inventTable.ItemGroupId == "FURNITURE";

delete_from inventTable
    where inventTable.ItemGroupId == "COMPONENT";

insert_recordset target (ItemId, ItemName)
    select ItemId, ItemName from source
    where source.ItemGroupId == "RAWMAT";`}</Snippet>

All three need a transaction, none needs `forupdate` — there is no buffer to select for
update, because no row ever reaches your code.

That last point is the trade-off. Set-based statements are fast precisely because they do
not run your X++ per row: no field-by-field logic, no conditional decisions, no calls out
to other methods. If you genuinely need to look at each row to decide what to do, a loop is
the right answer and the trace will honestly show the cost.

<Compare
  cal={`Item.SETRANGE("Item Category Code", 'FURNITURE');
IF Item.FINDSET(TRUE) THEN
  REPEAT
    Item.Blocked := TRUE;
    Item.MODIFY;
  UNTIL Item.NEXT = 0;`}
  xpp={`update_recordset inventTable
    setting Blocked = NoYes::Yes
    where inventTable.ItemGroupId == "FURNITURE";`}
/>

<NavCallout>
  **C/AL has `MODIFYALL`, and it is not the same thing.** `MODIFYALL` sets one field across
  a filtered set, and it still runs the `OnModify` trigger per record unless you pass
  `FALSE` — so the loop is hidden rather than removed. X++'s `update_recordset` sets several
  fields at once and genuinely does not touch each row, which is why it can be a single
  statement. The corollary is the thing to remember: it does **not** run the table's
  `update()` method. If a table has logic that must run on every change, a set-based
  statement will skip it, and F&O will silently fall back to a row-by-row loop in some
  cases for exactly that reason.
</NavCallout>
