## Writing is three steps, always

Every write in X++ has the same shape: get a buffer into the state you want, then call a
method on it.

<Snippet lang="xpp">{`InventTable inventTable;

ttsbegin;
inventTable.ItemId      = "F-500";
inventTable.ItemName    = "Standing desk";
inventTable.ItemGroupId = "FURNITURE";
inventTable.insert();
ttscommit;`}</Snippet>

Note what is missing: you never name the table again after the declaration, and you never
build a SQL statement. The buffer knows what table it is, and `insert()` sends whatever is
currently in it.

`update()` and `delete()` work the same way, with one extra requirement — the record has to
have been read with `forupdate`:

<Snippet lang="xpp">{`ttsbegin;
select forupdate inventTable
    where inventTable.ItemId == "F-500";

inventTable.ItemName = "Standing desk, electric";
inventTable.update();
ttscommit;`}</Snippet>

<Compare
  cal={`Item.INIT;
Item."No." := 'F-500';
Item.Description := 'Standing desk';
Item.INSERT(TRUE);`}
  xpp={`inventTable.clear();
inventTable.ItemId = "F-500";
inventTable.ItemName = "Standing desk";
inventTable.insert();`}
/>

## clear() is not optional

A buffer keeps its values after a write. Insert two records in a row without clearing and
the second one inherits every field you did not overwrite — including, usually, a key that
is now a duplicate:

<Snippet lang="xpp">{`ttsbegin;
inventTable.ItemId = "F-500";
inventTable.ItemName = "First";
inventTable.insert();

inventTable.clear();          // <-- without this, the next insert
inventTable.ItemId = "F-501"; //     still carries ItemName "First"
inventTable.ItemName = "Second";
inventTable.insert();
ttscommit;`}</Snippet>

C/AL's `INIT` is the same idea, and forgetting it causes the same class of bug. The
difference is that X++ will often let you get away with it right up until the moment a
unique index catches you, and then you get a duplicate key error pointing at a field you
did not think you had set.

## What a duplicate key looks like

Insert a record whose key already exists and the write fails with
`Exception::DuplicateKeyException`. It is one of only two exceptions that can be caught
*inside* the transaction that raised it — which is lesson 8's territory, but worth knowing
now, because it means a `try`/`catch` around an insert actually works.

<NavCallout>
  **`INSERT(TRUE)` has no direct equivalent, and the reason is instructive.** In C/AL the
  boolean says whether to run the `OnInsert` trigger; `INSERT(FALSE)` skips your own
  business logic, which is why it is both useful and dangerous. X++ inverts the default:
  `insert()` always runs the table's `insert()` method, and the escape hatch is a
  *different method*, `doInsert()`, which writes the row and runs nothing. So the risky
  choice is the one you have to name explicitly, rather than a boolean that is easy to
  flip by accident. Neither `doInsert()` nor table-method overrides are simulated here —
  they need the metadata layer — so this lesson stays on `insert()`.
</NavCallout>

## validateWrite, in prose only

Real F&O calls `validateWrite()` before a write from a form, and you override it to reject
bad data. It reads field properties — mandatory flags, string lengths, relations — from the
AOT metadata, and this simulator does not have that layer yet. Rather than let you practise
against a version that always returns `true`, the engine refuses to run it and says so. It
arrives with the forms track.
