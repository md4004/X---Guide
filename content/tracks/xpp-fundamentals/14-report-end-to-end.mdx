<Step id="four-elements">

Lesson 10 built half a report — a provider filling a table. This is the other half, and
the reason reports feel opaque until somebody shows you: **four elements**, only three of
which you write, connected by attributes rather than by calls.

| Element | What it is | Who writes it |
| --- | --- | --- |
| **Temporary table** | The rows the design prints | you |
| **Data contract** | The parameters the user is prompted for | you |
| **Data provider (RDP)** | The X++ that fills the table | you |
| **Report** | The design, its dataset binding, its grouping | you, in the designer |

Nothing in your code calls anything else in your code. The **controller** is handed a
report *name*, and everything after that is the framework following metadata.

In Visual Studio you create them from **Solution Explorer ▸ right-click the project ▸
Add ▸ New Item**, under **Dynamics 365 Items**:

- **Data Model ▸ Table** for the temp table, then set its **Table Type** property to
  `TempDB` or `InMemory`
- **Code ▸ Class** for the contract and the provider
- **Reports ▸ Report** for the report itself

</Step>

<Step id="the-contract">

## The contract is parameters, and nothing else

A data contract is a class of `parm` methods. The attributes are what make it a contract
rather than a bag of getters:

<Snippet lang="xpp">{`[DataContractAttribute]
class ItemSalesContract
{
    private str itemGroup;

    [DataMemberAttribute("ItemGroup")]
    public str parmItemGroup(str _itemGroup = itemGroup)
    {
        itemGroup = _itemGroup;
        return itemGroup;
    }
}`}</Snippet>

`[DataContractAttribute]` on the class says "these are report parameters". The name inside
`[DataMemberAttribute("ItemGroup")]` is the name the **report design** sees — not the
method name, not the field name. Rename `parmItemGroup` and nothing breaks. Change the
string and the design loses its parameter.

That indirection is the whole trick, and it is the same trick twice more in this lesson.

</Step>

<Step id="the-provider">

## The provider fills a table and hands it over

<Snippet lang="xpp">{`class ItemSalesDP extends SRSReportDataProviderBase
{
    private TmpItemSales tmpItemSales;

    [SRSReportDataSetAttribute("ItemSales")]
    public TmpItemSales getItemSales()
    {
        return tmpItemSales;
    }

    public void processReport()
    {
        // Fill tmpItemSales here.
    }
}`}</Snippet>

Three things are doing work:

- **`extends SRSReportDataProviderBase`** gives you `parmQuery()` and `parmDataContract()`.
  You do not set them — the framework does, before it calls you.
- **`processReport()`** is an override. It is the only method here the framework calls, and
  the only one that is yours to write.
- **`[SRSReportDataSetAttribute("ItemSales")]`** marks the getter the design binds to. Found
  by the attribute, not by the name.

<Aside title="SRSReportDataProviderBase is our own teaching stub">
  This simulator ships a minimal stand-in for that base class, written in X++ and clearly
  labelled — not Microsoft's source. It gives you `parmQuery`, `parmDataContract` and an
  empty `processReport` to override, which is the surface the lesson needs.
</Aside>

</Step>

<Step id="the-controller">

## The controller is four lines

A menu item does not point at your provider. It points at a **controller**, and the usual
one is three lines of setup and a go:

<Snippet lang="xpp">{`class ItemSalesController
{
    public static void main(Args _args)
    {
        SrsReportRunController controller = new SrsReportRunController();

        controller.parmReportName(ssrsReportStr(ItemSalesReport, Report));
        controller.parmArgs(_args);
        controller.startOperation();
    }
}`}</Snippet>

`ssrsReportStr(Report, Design)` is a compile-time function: it produces the string
`"ItemSalesReport.Report"` and fails the build if either half does not exist.

`startOperation()` is where the framework takes over. In order, it:

1. resolves the report element, and through it the provider class
2. constructs the provider
3. calls `parmQuery()` with the report's query
4. calls `parmDataContract()` with the parameters the user chose
5. calls **`processReport()`** — your code, and only now
6. reads the dataset back through the `[SRSReportDataSetAttribute]` getter

Step 5 is the only one you wrote. Steps 3, 4 and 6 are why the attributes exist.

<Aside title="Extending the controller">
  When a controller does need extending, the documented rule is narrow: override
  `prePromptModifyContract` or `preRunModifyContract`, and nothing else. Everything else in
  that class is the framework's business.
</Aside>

</Step>

<Step id="run-it">

## Your turn

Run the report you just built.

Keep your `ItemSalesDP` from before, and below it write the controller code:

- a `SrsReportRunController`
- `parmReportName("ItemSalesReport.Report")`
- `startOperation()`

You write no call to `ItemSalesDP` at all. The framework finds it, because the
**ItemSalesReport** element names it as its data provider.

Open the **Report** tab when it passes — that is the design's grouping and totals applied
to the rows your provider wrote.

</Step>

<Step id="the-design">

## The design is metadata, not code

Look at the report you just ran. The grouping by item group, the summed amounts, the
title — none of that is in your X++. It is on the **report element**:

| Property | Value here |
| --- | --- |
| Data provider | `ItemSalesDP` |
| Dataset | `ItemSales` |
| Group by | `ItemGroupId` |
| Totals | `sum(LineAmount)`, `sum(SalesQty)` |

In Visual Studio you reach it by double-clicking the report in **Solution Explorer**, which
opens the report designer. From there:

- **Datasets ▸ your dataset ▸ Properties** — set **Data Source Type** to
  `Report Data Provider`, then pick the class through the **Query** property's `...` button
- drag the dataset onto **Designs** to get an **AutoDesign**
- right-click a field under the design to add **Groupings** and **Totals**
- select the design and press **Preview** to run it without leaving the designer

That separation is why "the numbers are wrong" and "the layout is wrong" are two different
bugs with two different owners.

</Step>

<Step id="where-it-breaks">

Four failures, and what each one actually means:

| Symptom | Cause |
| --- | --- |
| "There is no report called X" | The controller's report name does not match the element |
| Report runs, prints nothing | The provider filled the table but nothing carries `[SRSReportDataSetAttribute]` |
| Parameters missing from the dialog | A `parm` method has no `[DataMemberAttribute]` |
| Rows correct, grouping wrong | The design, not your code — nothing in X++ decides grouping |

The last one is the one worth internalising. If the rows are right, stop reading your X++.

<KeyPoints>
  - Four elements: temp table, contract, provider, report — you write three
  - Attributes are the wiring; names are not
  - The framework calls `processReport()`, and it calls it *after* setting the query and
    the contract
  - Grouping and totals are design properties, not provider logic
</KeyPoints>

</Step>
