<Step id="one-table">

## One table, every company

F&O has exactly **one** `InventTable`, however many legal entities are configured. Every row
carries a `DataAreaId` — a short legal entity code — and every query you write is silently
filtered by it:

<Snippet lang="xpp">{`InventTable inventTable;

while select inventTable
{
    info(inventTable.ItemId);
}`}</Snippet>

That looks unfiltered. It is not. The generated SQL has a `WHERE DATAAREAID = ?` in it that
you never typed. Run it and check the trace — the predicate is right there.

The practical consequence is worth sitting with: the same `ItemId` can exist in several
companies as several **different rows**, with different names, costs, currencies, everything.
`C-1000` in one entity has nothing to do with `C-1000` in another beyond the coincidence of
the key.

<Aside title="The failure mode this creates">
  You will not write to the wrong company by accident — the scope is in the statement, not in
  your session. What you will do is write a query that quietly returns nothing because you
  were in the wrong company, and wonder why the table looks empty. An unexpectedly empty
  result is the symptom to learn.
</Aside>

</Step>

<Step id="changecompany">

## changecompany: borrow a company for a moment

<Snippet lang="xpp">{`CustTable custTable;

changecompany ("KELT")
{
    select firstonly custTable
        where custTable.AccountNum == "C-1000";

    info(custTable.CurrencyCode);   // KELT's C-1000, not ours
}`}</Snippet>

Inside the block, every buffer reads and writes as though you were signed in to that
company. Outside it, everything is back to normal — including when the block exits through
an error.

The catch, and it is a sharp one: **the buffer must be declared before the block and
re-selected inside it.** A buffer that already holds a row keeps that row. `changecompany`
changes where the *next* query looks, not what you are already holding.

</Step>

<Step id="crosscompany">

## crosscompany: all of them at once

<Snippet lang="xpp">{`CustTable custTable;

while select crosscompany custTable
{
    info(strFmt("%1 in %2", custTable.AccountNum, custTable.DataAreaId));
}`}</Snippet>

`crosscompany` removes the filter entirely. You get every row from every legal entity, and
`DataAreaId` becomes a field worth reading — it is now the only thing telling two
otherwise-identical rows apart.

Use it for reporting and for genuinely cross-entity logic. Do not reach for it by reflex: a
`crosscompany` query on a large table scans everything the company filter would normally
have excluded, and no index will save you.

<Aside title="Not every table is scoped">
  `DirPartyTable` — the global registry of people and organisations — is a **shared** table.
  One row is visible from every company and no `DataAreaId` filter is applied at all. That is
  how one legal person can be a customer in three entities without being stored three times.
</Aside>

</Step>
