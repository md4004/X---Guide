<Step id="stored-somewhere-else">

Financial dimensions are how a business slices its numbers: cost centre, department,
project, business unit. On screen they look like a couple of extra fields on a customer.

In the database they are nothing of the sort. Read a customer and look at what
`DefaultDimension` actually holds:

<Snippet lang="xpp">{`CustTable custTable;

select firstonly custTable where custTable.AccountNum == "C-1000";
info(strFmt("DefaultDimension = %1", custTable.DefaultDimension));`}</Snippet>

A number. `DefaultDimension` is a `RecId` pointing at a row in
**DimensionAttributeValueSet**, and that row is little more than an identity — the values
themselves hang off it, one row each, in **DimensionAttributeValueSetItem**.

So "this customer has a cost centre" is stored across four tables:

| Table                              | Holds                                       |
| ---------------------------------- | ------------------------------------------- |
| `DimensionAttribute`               | the dimension itself — `CostCenter`         |
| `DimensionAttributeValue`          | a value of it — `CC-100`                    |
| `DimensionAttributeValueSet`       | a set, which is just something to point at  |
| `DimensionAttributeValueSetItem`   | one row per value in that set               |

Run it, then open the SQL trace.

<Aside title="This is why dimension bugs are hard">
  Nothing about a customer record tells you what its dimensions are. You cannot read them
  without three joins, which is why so much dimension code is written by guesswork. Learn
  the query once and the guesswork stops.
</Aside>

</Step>

<Step id="follow-the-chain">

## Your turn

Read customer `C-1000` and log its financial dimensions, one per line, in the form:

`CostCenter = CC-100`

Start from `DimensionAttributeValueSetItem`, filtered to the customer's `DefaultDimension`.
Join to `DimensionAttributeValue` to reach the dimension it belongs to, then to
`DimensionAttribute` for the name. The item already carries the `DisplayValue`, so you do
not need to go back for it.

Do it in one query — the joins are the whole point.

</Step>

<Step id="empty-is-not-stored">

The framework stores a row only for a dimension that has a value. A dimension left blank
has **no row at all**.

That has a consequence people trip over constantly: once the data is saved, a dimension
that was never filled in and a dimension that a user deliberately cleared look identical.
There is nothing to tell them apart, because in both cases there is nothing there.

The documented workaround is to create a real dimension value that means "empty" — named
`empty`, `n/a` or `*blank*` — so a user can choose it and leave a trace.

The same rule applies one level up. A record with no dimensions at all does not point at
an empty set; it points at nothing, and a `RecId` of nothing is `0`:

<Snippet lang="xpp">{`CustTable custTable;

while select custTable where custTable.DefaultDimension == 0
{
    info(strFmt("%1 has no dimensions", custTable.AccountNum));
}`}</Snippet>

</Step>

<Step id="never-updated">

Dimension records are **immutable**. They are written once and never updated or deleted.

Add a value to a customer's dimensions and the framework does not add a row to the
existing set. It creates a **new** set, writes a full copy of the values into it, and
repoints the customer at the new set. The old set is left exactly as it was.

That sounds wasteful until you think about what is pointing at it. A posted voucher from
last year references a dimension set. If somebody edits the customer's cost centre today
and that edit rewrote the set in place, the historical voucher would silently change
meaning. Immutability is what stops your accounts from rewriting themselves.

<Aside title="What this means for your code">
  Never write an `update()` against a dimension table. If you find yourself wanting to, you
  are working against the framework — build a new set instead, and repoint the record at it.
</Aside>

</Step>

<Step id="merging">

Documents collect dimensions from several places at once. A sales order line can take them
from the order header, from the customer, and from the item — and something has to decide
which wins.

The rule is **the target wins**:

- If the target already has a value for a dimension, the source is ignored.
- If the target is blank for a dimension, the source's value is copied in.

Microsoft publishes a worked example of this. Merging an item's dimensions into a line that
already has some produces:

| Dimension    | Target  | Item    | Merged  | Why                                    |
| ------------ | ------- | ------- | ------- | -------------------------------------- |
| BusinessUnit |         |         |         | blank in both                          |
| CostCenter   |         | 008     | 008     | blank on the target, so copied         |
| Department   | 027     | 023     | 027     | already set on the target, so skipped  |
| ItemGroup    |         | AudioRM | AudioRM | blank on the target, so copied         |
| Project      | 000003  |         | 000003  | already set on the target              |

`Department` is the row worth staring at. The item carried `023` and it lost. Merging is
**not** last-writer-wins, and code written on that assumption produces a defaulting bug
that only appears on the documents where both sources happen to be filled in.

</Step>

<Step id="merge-two-sets">

## Your turn

Merge item `F-100`'s dimensions into customer `C-1000`'s, with the **customer** as the
target, and log the result one line per dimension in the form:

`CostCenter = CC-100`

The customer has `CostCenter` and `Department`. The item has `CostCenter` and `ItemGroup`.
Applying the rule, the merged set is three dimensions — and the item's `CostCenter` is not
one of them.

Log the target's own values first, then walk the item's and log only those the customer
does not already have a value for. To decide that, look for an item in the customer's set
whose value belongs to the same `DimensionAttribute`.

</Step>

<Step id="in-a-real-environment">

You have just done by hand what a real environment gives you an API for. It is worth
knowing the names, because you will read them in standard code long before you write them:

<Snippet lang="xpp">{`// Reading and building a set of default dimensions
DimensionAttributeValueSetStorage storage;

// Merging, with exactly the precedence you implemented above
DimensionDefault merged = DimensionDefaultFacade::serviceMergeDefaultDimensions(
    targetDimension,
    sourceDimension);

// Combining dimensions with a main account to make a ledger account combination
LedgerDimensionAccount ledgerDimension = LedgerDimensionFacade::serviceCreateLedgerDimension(
    defaultAccount,
    mergedDimension);`}</Snippet>

Two things to take away from those signatures.

**Default dimensions carry every dimension except the main account.** A ledger account
combination is a main account plus a set of dimension values, ordered by the account
structure — which is why creating one takes a separate call that supplies the account.

**These APIs are not simulated here.** Account structures, advanced rules, and the
posting-time validation that decides whether a combination is even legal are a large piece
of machinery, and a version of it that was wrong in the details would be worse than not
having it. What you have learned is the data model underneath, and that part does not
change.

<KeyPoints>
  - `DefaultDimension` is a `RecId` pointing at a set, not a value
  - A dimension with no value has no row, so cleared and never-set are indistinguishable
  - Dimension records are never updated — a change writes a new set
  - When two sets merge, the target's existing values win
</KeyPoints>

</Step>
