<Step id="what-a-form-is">

## A form is metadata over a query

There is no HTML behind an F&O form and no layout code you write by hand. A form is a
small pile of declarations:

- **data sources** — which tables it reads, and whether they are editable
- **a design** — a tree of controls, each bound to a data source field
- **a pattern** — `SimpleList`, `Details` and friends, which fix the overall shape

Everything else the form does — fetching rows, rendering a grid, showing an enum by its
name rather than its number, greying out a read-only field — is the platform reading that
metadata and acting on it.

Press **Check** and open the **Form** tab. That grid is `InventTableListPage` rendered from
its metadata over the rows that are actually in the database right now.

<Aside title="What this is not">
  This renders a form's data and layout. It does not run a form: there are no data source
  events, no `element.args()`, no lookup forms, no `super()`. You will learn what a form is
  made of, which is genuinely useful, and you will not learn to write form code here.
</Aside>

</Step>

<Step id="properties-render">

## Properties are not decoration

Every column in that grid got its appearance from a property, not from a guess:

| Property     | What the form does with it                             |
| ------------ | ------------------------------------------------------ |
| `Mandatory`  | marks the field, and refuses to save the record without it |
| `AllowEdit`  | `No` renders the control read-only                     |
| enum type    | `NoYes` becomes a checkbox, anything else a combo box  |
| EDT          | supplies the label, the help text and the string length |

Look at the form again. `Item number` carries a red `*` and is greyed — it is mandatory and
`AllowEdit` is `No`, because a primary key you can retype is a primary key you can corrupt.
`Stopped` shows `Yes`/`No`, not `1`/`0`.

An **EDT** — extended data type — is the reason `ItemId` looks the same everywhere it
appears. Define the type once with its size and label, use it on twenty tables, change it in
one place.

</Step>

Change some data and watch the form follow it.

Rename `F-100` to `Ashwood desk, refreshed` and set its `Blocked` to `NoYes::Yes`.

Then open the **Form** tab. Your row is highlighted, and `Stopped` reads `Yes` — not `1`,
because the form resolves the enum through its metadata.

</Step>

<Step id="validatewrite">

## validateWrite is the check a form runs

When a user saves a record on a form, the form engine calls `validateWrite()` on the table
first. That method returns a **boolean**: `true` if the record may be written.

<Snippet lang="xpp">{`InventTable inventTable;

inventTable.ItemName = "A desk with no item number";

if (!inventTable.validateWrite())
{
    info("The form would have refused to save this.");
}`}</Snippet>

It reports; it does not write, and it does not throw. That is what lets you write
`if (buffer.validateWrite())` at all.

Run the example. The Infolog gets an error naming the missing field, and then the `info`
line — because `validateWrite` returning `false` is a value, not an exception.

</Step>

<Step id="reject-a-record">

## Your turn

Build an item that is missing its `ItemId`, ask `validateWrite()` about it, and log

`Rejected`

when it says no.

Do not insert anything. The whole point is to find out *before* writing.

</Step>

<Step id="nothing-calls-it">

## Nothing calls it for you

Here is the part that costs people data.

`insert()` does **not** call `validateWrite()`. Neither does `update()`. The form engine
calls it, and the data-entity paths call it — but a plain buffer write from X++ calls
nothing and checks nothing:

<Snippet lang="xpp">{`ttsbegin;
inventTable.ItemName = "No item number at all";
inventTable.insert();      // succeeds. Nothing validated anything.
ttscommit;`}</Snippet>

So a record that a user could never have created through the form lands in the table,
because your job wrote it directly.

<Aside title="The habit">
  If your code writes what a user would otherwise type, call `validateWrite()` yourself and
  respect the answer. The one-line version is
  `if (!buffer.validateWrite()) throw error("...");` — check it, and stop if it fails.
</Aside>

</Step>

<Step id="validate-then-insert">

## Your turn

Do it properly. Insert item `F-700` named `Validated desk` in group `FURNITURE`, but only
after `validateWrite()` agrees.

- if it agrees, insert and log `Inserted after validating`
- if it does not, log `Refused` and insert nothing

Then check the **Form** tab: your record is in the grid.

</Step>

<Step id="not-modelled">

## What is deliberately missing

Worth knowing about, and not simulated here, because a simulation of them would be
guesswork:

- **`validateDelete()`** — depends on delete actions between tables, which this environment
  does not model. It refuses to run rather than tell you a delete is safe.
- **Relations and mandatory foreign keys** — declared in the schema, not enforced.
- **Form extensions, data source events, `super()`** — the customisation track.

The rule this project follows: an incomplete simulation is fine, a wrong one is not.

</Step>
