<Step id="shape">

## Writing always has the same shape

Get a buffer into the state you want, then call a method on it:

<Snippet lang="xpp">{`InventTable inventTable;

ttsbegin;
inventTable.ItemId      = "F-500";
inventTable.ItemName    = "Standing desk";
inventTable.ItemGroupId = "FURNITURE";
inventTable.insert();
ttscommit;`}</Snippet>

Notice what is missing. You never name the table again after the declaration, and you never
build a statement by hand. The buffer already knows what table it belongs to, and
`insert()` sends whatever is currently sitting in it.

A new record needs no `select` at all. The buffer starts empty, which is exactly the state
an insert wants.

</Step>

<Step id="updating">

## Updating and deleting

`update()` and `delete()` have the same shape, with one extra requirement — the record must
have been read with `forupdate`:

<Snippet lang="xpp">{`ttsbegin;
select forupdate inventTable
    where inventTable.ItemId == "F-500";

inventTable.ItemName = "Standing desk, electric";
inventTable.update();
ttscommit;`}</Snippet>

One `update()` writes the whole buffer, so set every field you want to change before you
call it. Two changes do not need two updates.

`delete()` is shorter still: select it for update, then call `inventTable.delete();`.

</Step>

</Step>

<Step id="clear">

## clear() is not optional

A buffer keeps its values after a write. Insert two records in a row without clearing and
the second inherits every field you did not overwrite — including, usually, a key that is
now a duplicate:

<Snippet lang="xpp">{`ttsbegin;
inventTable.ItemId = "F-500";
inventTable.ItemName = "First";
inventTable.insert();

inventTable.clear();          // <-- without this, the next insert
inventTable.ItemId = "F-501"; //     still carries ItemName "First"
inventTable.ItemName = "Second";
inventTable.insert();
ttscommit;`}</Snippet>

`clear()` really does empty the buffer, so after it you have to set **every** field again,
not just the ones that change.

<Aside title="What a duplicate key looks like">
  Insert a record whose key already exists and the write fails with
  `Exception::DuplicateKeyException`. It is one of only two exceptions that can be caught
  *inside* the transaction that raised it — the last lesson explains why that is unusual.
</Aside>

</Step>

<Step id="not-simulated">

## Two things this simulator will not fake

**`doInsert()`** writes the row and skips the table's own `insert()` logic. It exists, it is
occasionally the right call, and it is not simulated here — table method overrides need the
metadata layer.

**`validateWrite()`** runs before a write from a form and is where you reject bad data. It
reads field properties — mandatory flags, lengths, relations — from metadata this engine
does not model yet.

Rather than let you practise against a version that always returns `true`, the engine
refuses to run either and tells you so. A simulation that is incomplete is fine; one that is
quietly wrong is not.

</Step>
