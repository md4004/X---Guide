<Step id="buffers">


To touch a table you declare a variable of that table's type:

<Snippet lang="xpp">{`InventTable inventTable;`}</Snippet>

That is a **table buffer**. It holds **one record at a time**, it starts empty, and you
fill it with a `select`. By convention the variable is the table name with a lowercase
first letter.

To read a single record, ask for one:

<Snippet lang="xpp">{`select firstonly inventTable
    where inventTable.ItemId == "F-100";

info(inventTable.ItemName);`}</Snippet>

`firstonly` matters. Without it the database prepares the whole result set and you have
paid to read everything in order to look at one row. Run the example and open the **SQL
trace** tab — you will see a `LIMIT` in the generated statement.

Note `==` for comparison. A single `=` is assignment, as in most languages.

</Step>

<Step id="select-one-item">

## Your turn

The buffer is declared for you. Read the item whose `ItemId` is `F-100` and log its
`ItemName`.

Use `firstonly` — you only want one record.

</Step>

<Step id="empty">


A `select` that finds nothing does not raise anything. It leaves the buffer empty, and
every field comes back as the starting value for its type — `""` for a `str`, `0` for an
`int`.

So you test the buffer by reading a field from it:

<Snippet lang="xpp">{`select firstonly custTable
    where custTable.AccountNum == "NOPE";

if (!custTable.AccountNum)
{
    info("No such customer");
}`}</Snippet>

Every record also has a `RecId` — a unique number the database assigns. `if (buffer.RecId)`
is the idiomatic "did I find anything", because a real record can never have a RecId of
zero.

</Step>

<Step id="loops">


`while select` opens a cursor and loops it in a single statement:

<Snippet lang="xpp">{`while select inventTable
    where inventTable.ItemGroupId == "FURNITURE"
{
    info(inventTable.ItemName);
}`}</Snippet>

The filter and the loop are the same statement. There is no separate "apply a filter" step
and no "move to the next record" call — the `where` belongs to the `select` that opens the
cursor, so it cannot leak into a later query by accident.

Run it and check the SQL trace: **one** statement, however many rows come back.

</Step>

<Step id="forupdate">


A buffer filled by a plain `select` is **read-only**. If you intend to change what you
read, say so when you read it:

<Snippet lang="xpp">{`ttsbegin;
while select forupdate inventTable
    where inventTable.ItemGroupId == "FURNITURE"
{
    inventTable.Blocked = NoYes::Yes;
    inventTable.update();
}
ttscommit;`}</Snippet>

Leave out `forupdate` and the update fails, because the record was never locked for
writing. That is the database protecting you from losing someone else's concurrent change.

<Aside title="Two things at once">
  Writes also have to sit inside `ttsbegin` / `ttscommit`. That is the next lesson — for
  now, copy the pair whenever you write.
</Aside>

</Step>

<Step id="block-furniture">

## Your turn

Set `Blocked` to `NoYes::Yes` on every item in the `FURNITURE` group, counting as you go.

Then log:

`Blocked N items`

You will need `forupdate` on the select, a `ttsbegin` / `ttscommit` pair around the loop,
and a call to `update()` inside it.

</Step>
