<Step id="a-select-you-assemble">

A `while select` is written when you write the code. A **query object** is assembled while
the code runs — which is what you need when the filter comes from a parameter, a form, or
a report contract, rather than from you.

<Snippet lang="xpp">{`Query query = new Query();
QueryBuildDataSource qbds = query.addDataSource(tableNum(InventTable));

QueryRun queryRun = new QueryRun(query);
InventTable inventTable;

while (queryRun.next())
{
    inventTable = queryRun.get(tableNum(InventTable));
    info(inventTable.ItemId);
}`}</Snippet>

Four types, and each is exactly what its name says:

| Type | Is |
| --- | --- |
| `Query` | the whole statement |
| `QueryBuildDataSource` | one table in it |
| `QueryBuildRange` | one filter on that table |
| `QueryRun` | the execution, and the cursor |

Run it, then **open the SQL trace**. It is a plain parameterised `SELECT` — the same one
the equivalent `while select` would produce. A query object is not a different mechanism.
It is the same mechanism, assembled at a different time.

</Step>

<Step id="ranges">

## A range is not an equals

`QueryBuildRange` filters a data source. The obvious use is equality:

<Snippet lang="xpp">{`QueryBuildRange qbr = qbds.addRange(fieldNum(InventTable, ItemGroupId));
qbr.value("FURNITURE");`}</Snippet>

But the value is a small **expression language**, not a literal, and this is where filters
go quietly wrong:

| You write | It means |
| --- | --- |
| `"FURNITURE"` | equals |
| `">200"` | greater than |
| `"<=10"` | less than or equal |
| `"F-100..F-200"` | between, inclusive |
| `"F-1*"` | starts with |
| `""` | **no restriction at all** |

That last row is the one that bites. An empty range does not match nothing — it filters
nothing, and the query returns everything. A parameter that arrives blank widens your
query rather than emptying it.

<Aside title="queryValue() is how you get a literal in safely">
  When the value comes from a variable — especially an enum — wrap it:
  `qbr.value(queryValue(someValue))`. It formats the value the way the range parser
  expects, and it is the habit that stops a stray `*` in user input from becoming a
  wildcard.
</Aside>

</Step>

<Step id="find-before-add">

## Find before you add

Real framework code almost never calls `addRange` on its own. It does this:

<Snippet lang="xpp">{`QueryBuildDataSource qbds = query.dataSourceTable(tableNum(InventTable));
QueryBuildRange qbr = qbds.findRange(fieldNum(InventTable, ItemGroupId));

if (!qbr)
{
    qbr = qbds.addRange(fieldNum(InventTable, ItemGroupId));
}

if (!qbr.value())
{
    qbr.value("FURNITURE");
}`}</Snippet>

Read it as a sentence: *is there already a range on this field? If not, add one. Does it
already have a value? If not, set mine.*

The reason is that the query may have arrived from somewhere else — a report contract, a
form's data source, a user's filter — and a plain `addRange` would add a **second** range
next to the user's, quietly narrowing their results. This is the exact shape the report
data provider walkthrough uses, and it is worth copying.

</Step>

<Step id="a-view-is-a-saved-select">

## A view is a select somebody got tired of writing

A **view** is an AOT element that wraps a query and behaves like a table. You select *from*
it, and the join it hides runs underneath:

<Snippet lang="xpp">{`CustSalesOrderView custSalesOrderView;

while select custSalesOrderView
{
    info(strFmt("%1 for %2 (%3)",
        custSalesOrderView.SalesId,
        custSalesOrderView.CustAccount,
        custSalesOrderView.CustGroup));
}`}</Snippet>

`CustGroup` is not on `SalesTable`. It lives on `CustTable`, and the view is what brings it
across — the same de-normalising job a data entity does, one layer lower and read-only.

A view is not a table, and the differences are the ones you would expect:

| | Table | View |
| --- | --- | --- |
| Storage | its own | none |
| Insert / update / delete | yes | no |
| Indexes | its own | the underlying tables' |
| Reading it costs | one query | one query, with the join inside |

In Visual Studio: **Add ▸ New Item ▸ Data Model ▸ View**, then drag tables onto its
**Metadata ▸ Data Sources** node and fields onto **Fields**.

<Aside title="The one that leaks data">
  A company-scoped view **must select `DATAAREAID`**. It still works without it — it still
  returns rows — but the scoping predicate has nothing to bind to, so every read silently
  returns every company's data. That is invisible in a one-company test environment, and it
  is exactly how a convenience becomes a security incident.
</Aside>

</Step>

<Step id="when-to-use">

## When a query object earns its place

Use one when the shape of the query is **not known when you write the code**:

- a report's filter comes from the contract the user filled in
- a form's data source is filtered by what the user typed
- a lookup is narrowed by a parameter

Use a `while select` when it is known — which is most of the time in your own business
logic. A query object is more code and more indirection; it buys you runtime shape, and
nothing else.

**What this simulator does not do.** Joining one data source to another —
`qbds.addDataSource(...)`, `joinMode`, `relations` — is out of scope here, and asking for
it says so rather than quietly running half the query. Write the join as a
`while select ... join ...`; the SQL trace will show you they are the same thing.

<KeyPoints>
  - A query object is a `select` assembled at runtime, and compiles to the same SQL
  - Ranges are an expression language: `>`, `..`, `*` — and empty means *no filter*
  - `findRange` before `addRange`, or you narrow somebody else's query
  - Reach for one when the shape is a runtime decision, not before
</KeyPoints>

</Step>
